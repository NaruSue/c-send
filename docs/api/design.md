# API 機能設計書

## 1. 目的

c-send の定型文またはクリップボードの内容を API へ送信し、API の結果を確認・再利用できるようにする。

初期実装は Windows ネイティブ版に限定する。ネイティブ版の API 対応が完成するまでは、PWA 版・HTA 版など他の版へ機能を派生させない。

## 2. 対応方針

### 2.1 対応サービス

v2.0ではGemini、OpenAI、Anthropic Claude API、GitHub REST API、Open-Meteo Weather APIの設定JSONをサンプルとして同梱する。これらはサービス固有のコードではなく、共通の設定JSONと通信処理で利用する。

今後の対象サービスは固定の優先順位では決めない。公式資料が現行の汎用通信仕様へ収まる場合は、設定JSON、認証情報取得ガイド、カテゴリサンプルを追加する。収まらない認証方式や通信方式が必要な場合は、特定サービス専用コードではなく、複数サービスで再利用できる汎用機能として設計して追加する。

### 2.2 汎用 API としての設計

Gemini 専用機能として固定せず、API ごとに HTTP メソッド、エンドポイント、認証情報、リクエスト、レスポンスを定義できる構成にする。

API によって `GET`、`POST`、`PUT`、`DELETE` などのメソッドや、認証ヘッダー、固定ヘッダー、リクエスト JSON、レスポンス形式が異なるため、これらを API Action 単位で設定可能にする。

利用者への提供方法は次の2経路とする。

1. APIとJSONの知識を持つ利用者が、仕様書に従って設定JSONを直接カスタマイズする。
2. 一般利用者が、c-sendのAPI仕様書と利用したいAPIの公式資料をAIへ渡し、設定JSONと導入手順を作成してもらう。

現在の推奨経路は2とする。[API設定JSON仕様](config-spec.md)へ、設定JSON、認証情報の登録、API項目の作成、動作確認までをAIに出力させるプロンプトを収録する。GitHubで公開する仕様書、サービス別ガイド、設定JSON、カテゴリサンプルを、AIが参照できるカスタマイズ資料として継続的に整備する。

## 3. 利用イメージ

定型文の内容にプロンプトを記載し、必要な箇所へ現在の入力を埋め込んで送信する。

例:

```text
あなたは国立大学の教授で、とても細かいことまで指摘する厳しい人物として知られています。
次の{{clipboard}}を添削および評価し、寸評を1500文字以内で返してください。
```

この場合、API 実行開始時点のクリップボード内容を `{{clipboard}}` に展開して送信する。

## 4. 画面構成

### 画面共通表示要件

API リスト、API 詳細、API Action 詳細、設定 key 編集を含む API 関連の全画面は、`setting.ini` の `[font]` に設定されたフォント名とフォントサイズを使用する。ダイアログ本体だけでなく、ラベル、入力欄、コンボボックス、リスト、ボタンにも同じ設定フォントを適用し、OS またはダイアログテンプレートの既定フォントが混在しないようにする。

設定フォントが基準サイズより大きい場合は、文字だけを拡大せず、ダイアログ、各コントロール、余白、リスト列幅を同じ比率で拡大する。ボタン文字やラベルが欠けたり、コントロール同士が重なったりしない寸法を確保する。API 画面を初めて開いた時点から、全コントロールの配置と背景を完成した状態で描画する。

### 4.0 システムメニューのAPI入口

システムメニューのカテゴリ設定項目の下にセパレータを挿入し、その下に「API」項目を表示する。「API」と「バージョン情報（About）」の間にもセパレータを表示し、設定機能と製品情報を別グループとして扱う。

- `api`ディレクトリが存在する場合は「API」項目を表示する。
- `api`ディレクトリがない場合は「API」項目を表示しない。
- API項目を表示しない場合は、API用の追加セパレータも表示しない。
- API設定ファイルが0件でも、APIリスト画面を開いて新規設定を作成できるようにする。
- API設定ファイルが存在しない状態では、通常の定型文編集画面のAPIモードは利用不可とする。

### 4.0.1 APIリスト画面

「API」メニューからAPI定義ファイルの一覧を表示する。表示対象は`api/*.json`とする。

一覧にはAPIの表示名、設定ID、エンドポイント、登録Action数を表示する。設定ファイルがない場合は空状態を表示し、「新規作成」から最小構成のAPI設定を作成できるようにする。

### 4.1 API リスト画面

登録済み API の一覧を表示する。

表示項目:

- API 名称
- API 設定 ID
- 基本 URL
- 登録 Action 数

操作:

- 「追加」ボタンで API 詳細画面を新規モードで開く。
- 「編集」ボタンまたは一覧のダブルクリックで API 詳細画面を開く。
- API の削除は API 詳細画面ではなく API リスト画面から行う。
- 「閉じる」ボタンで画面を閉じる。

### 4.2 API 詳細画面

1 つの API サービスを定義する。

項目:

- サービス名称
- 基本 URL
- タイムアウト時間（既定値 120 秒）
- 認証タイプ
- クレデンシャル ID
- API token（API キーまたは Bearer の場合）
- ID／PASS（Basic 認証の場合）
- 設定 key 定義
- Action リスト
- Action 追加ボタン
- Action 編集ボタン
- Action 削除ボタン

認証タイプは次から選択するコンボボックスとする。

- 認証なし
- API キー・ヘッダー
- API キー・クエリ
- Bearer
- Basic

認証タイプを変更した場合は、必要な認証情報入力欄へ切り替える。API token、Basic 認証の ID／PASS は画面から Windows Credential Manager へ保存し、API 設定 JSON へは保存しない。空欄のまま API 設定を保存した場合は、Credential Manager にある既存の認証情報を維持する。

クレデンシャル ID は Credential Manager 内の保存単位を決める参照 ID とし、新規・既存を問わず編集可能とする。IDを変更した場合は変更後のIDに保存済みの認証情報を参照し、変更前の認証情報は自動移行・自動削除しない。同じ認証情報を再利用する複数のAPI設定では、同じクレデンシャルIDを指定できる。Basic 認証では 1 つのクレデンシャル ID を名前空間として使用し、その配下へ ID と PASS を別々に保存する。

設定 key 定義は、認証ヘッダー名、クエリ名、プレフィックスなど、サービスごとに異なる非機密設定を JSON として保存する。ただし画面では JSON 文字列をそのまま表示せず、「設定項目／値」の一覧へパースして表示・編集する。JSON 構文に戻せない値は保存不可とする。

API キーやトークンは通常の設定ファイルへ保存しない。ネイティブ版では Windows Credential Managerへ保存する。

認証情報は URL から自動判定せず、API 設定で明示した `credentialId` で分離する。表示名や基本 URL を変更しても Credential Manager の対象名は変わらない。`credentialId`を変更した場合だけ参照先が変わる。`/v1` と `/v2` で認証情報が異なる場合は別のクレデンシャル IDを、同じ認証情報を共有する場合は同じIDを使用する。詳細は[API認証方式仕様](auth-spec.md)を参照する。

### 4.3 API Action 詳細画面

API の個別操作を定義する。

項目:

- Action 名
- URL（API 詳細の基本 URL より後ろの相対 URL）
- HTTP メソッド
- Description（説明）
- Request JSON
- Response JSON

HTTP メソッドは `GET`、`POST`、`PUT`、`PATCH`、`DELETE` から選択する。基本 URL と相対 URL の `/` はアプリ側で正規化して結合する。

Request JSON と Response JSON は、インデントと改行を付けた整形済み JSON テキストとして表示・編集する。API仕様書をAIへ渡して生成・修正したJSONを、そのまま貼り付けられることを重視する。保存時にテキストをJSONとしてパースし、構文、必須項目、`{{value}}` の位置を検証する。ボディを送らない GET などのActionではRequest JSONを空欄にでき、HTTPリクエストにも本文と`Content-Type`を送らない。

Action ごとに定義できるようにし、API ごとの通信仕様の違いを吸収する。

#### Request JSON の `{{value}}`

Request JSON 内の文字列値 `{{value}}` は、定型文項目の `value` に `{{clipboard}}` などを展開した最終入力文字列へ置き換える。置換は文字列連結ではなく JSON 文字列値として行い、引用符、改行、バックスラッシュなどを安全にエスケープする。

例:

```json
{
  "contents": [
    {
      "parts": [
        {
          "text": "{{value}}"
        }
      ]
    }
  ]
}
```

#### Response JSON の `{{value}}`

Response JSON は実レスポンスから結果本文を抽出するための構造パターンとする。文字列値 `{{value}}` の位置を結果として取得する。

- オブジェクトのキーは実レスポンスと一致させる。
- 配列に 1 つのパターン要素を記載した場合、そのパターンを実配列の各要素へ適用する。
- 複数の `{{value}}` が取得された場合はレスポンス順を維持して連結する。
- `{{value}}` が 1 件も取得できない場合は結果形式エラーとする。

例:

```json
{
  "candidates": [
    {
      "content": {
        "parts": [
          {
            "text": "{{value}}"
          }
        ]
      }
    }
  ]
}
```

### 4.4 定型文編集画面のAPI選択UI

定型文編集画面でAPIラジオボタンを選択した場合、APIが複数存在しても実行対象を特定できるよう、APIとActionの選択欄を表示する。

- API選択欄：`api/*.json`のAPI一覧
- Action選択欄：選択したAPIに定義されたAction一覧
- HTTPメソッド：Action定義から読み取り専用で表示
- 実行 URL：API の基本 URL と Action の相対 URLを結合し、読み取り専用で表示

HTTPメソッドやエンドポイントはAction定義に含まれるため、編集画面で個別に入力・変更しない。APIまたはActionを変更した場合は、Actionの参照情報を更新する。

保存形式は既存の項目データ構造を使用する。

```json
{
  "mode": "api",
  "value": "次の{{clipboard|文章}}を要約してください。",
  "options": {
    "api": "gemini",
    "action": "generateContent"
  }
}
```

API定義またはAction定義が選択できない場合はAPIモードを選択できない状態にし、既存データの参照先が無効な場合は保存時にエラーを表示する。

API 項目は通常の定型文と同じ一覧内に表示し、項目右側の実行ボタンから API を実行する。結果が返った後は、結果アイコンのクリックで保持中の結果をクリップボードへコピーする。

ネイティブ版でAPI設定ファイルが存在しない場合は、API項目とAPIモード選択を表示せず、通常の定型文機能だけを利用可能にする。

## 5. カテゴリと項目の構成

API 専用カテゴリは作らず、既存のカテゴリ内に通常の定型文と API Action 項目を混在できるようにする。

項目の `mode` で処理種別を区別する。

```text
plain    通常の定型文
template テンプレート定型文
counter  カウンター付き定型文
api      API Action を実行する項目
```

API 項目の `value` はプロンプト本文またはリクエストテンプレートとして扱い、API サービスと Action の参照情報は `options` に保持する構成を基本とする。

例:

```json
{
  "name": "文章を添削",
  "value": "次の{{clipboard}}を添削し、1500文字以内で寸評を返してください。",
  "mode": "api",
  "options": {
    "api": "gemini",
    "action": "generateContent"
  }
}
```

この構成により、同じカテゴリの中で通常のコピー操作と API 実行操作を扱える。ネイティブ版と PWA 版でカテゴリ・項目の考え方を共有しやすくなり、将来の移植時に API 専用の別データ構造を作らずに済む。

API サービスの定義（エンドポイント、認証情報、Action 定義）は項目データとは分離して管理する。項目は API と Action を参照し、プロンプトや入力タグだけを保持する。

## 6. サンプル設定: Gemini API

### 6.1 初期 Action

Gemini API の同期 REST API `generateContent`を、生成API設定の基本例として同梱する。

```text
POST https://generativelanguage.googleapis.com/v1beta/models/{model}:generateContent
```

認証は `x-goog-api-key` ヘッダーを使用する。

モデル選択用のUIは設けない。Geminiではモデル名がURLに含まれるため、Actionのエンドポイントまたは設定ファイルへ記載する。他のサービスでモデル名がrequest JSONに必要な場合も同様に設定ファイルへ記載する。

例:

```text
https://generativelanguage.googleapis.com/v1beta/models/gemini-3.5-flash-lite:generateContent
```

### 6.2 Gemini リクエスト

```json
{
  "contents": [
    {
      "parts": [
        {
          "text": "{{value}}"
        }
      ]
    }
  ]
}
```

項目側の `{{input}}` や `{{clipboard}}` を先に展開し、その最終入力文字列を Request JSON の `{{value}}` へ JSON 文字列として安全に設定する。

### 6.3 Gemini レスポンス

Response JSON の `{{value}}` 位置から結果本文を取得する。

```json
{
  "candidates": [
    {
      "content": {
        "parts": [
          {
            "text": "{{value}}"
          }
        ]
      }
    }
  ]
}
```

複数の text パートがある場合は、順番を維持して連結する。結果本文が取得できない場合は、API エラーまたは結果なしとして扱う。

Gemini の詳細なエンドポイント、リクエスト、レスポンス仕様は [gemini.md](gemini.md) に記載する。共通の API 設定 JSON 形式は [config-spec.md](config-spec.md) に記載する。

## 7. 入力タグ

初期対応するタグは次の 2 つとする。

### `{{input}}`

現在選択している定型文の内容を展開する。

### `{{clipboard}}`

API 実行開始時点のクリップボード内容を展開する。

### `{{clipboard|代替文字列}}`

API 実行開始時点のクリップボードが空の場合に、`|` の後ろに記載した代替文字列を展開する。クリップボードに内容がある場合は、代替文字列を使用せずクリップボード内容を展開する。

例:

```text
次の{{clipboard|文章}}を箇条書きにしてください。
```

クリップボードが空の場合は「次の文章を箇条書きにしてください。」となる。代替文字列の前後にある空白は記法上の空白として除去し、文字列内部の空白は保持する。

API 実行中にクリップボードが変更されても、送信済みの入力内容は変化しないものとする。

タグは必要最小限から開始し、用途が明確になった場合のみ追加する。

## 8. 実行フロー

1. ユーザーが定型文または API Action を選択する。
2. API 実行開始時のクリップボード内容を取得して保持する。
3. 項目の `value` にある `{{input}}`、`{{clipboard}}` を展開して最終入力文字列を作る。
4. Request JSONがある場合だけ、`{{value}}` へ最終入力文字列を設定する。
5. HTTP メソッド、URL、認証情報、`keyConfig`の固定ヘッダー、必要なリクエスト本文を組み立てる。
6. API を実行する。
7. Response JSON の `{{value}}` 位置から結果本文を取り出す。
8. 実行した API 項目へ結果本文またはエラー内容を保存する。
9. API 実行開始時と現在のクリップボード内容を比較する。
10. 現在のクリップボードが開始時と同じ、または空の場合は、常に結果をクリップボードへコピーする。

現在のクリップボードが開始時から変更されていて、かつ空でない場合は、ユーザーの入力を保護するため結果で上書きしない。コピー直前にも必要に応じて再確認する。クリップボードを読み取れない場合は安全側で自動コピーしない。

## 9. API 項目ごとの状態と結果

初期実装ではユーザー向けの結果一覧画面は作成しない。ただし、内部メモリ上に結果レコードのリストを保持し、実行状態、完了結果、エラー、再コピーに利用する。必要に応じて一時ファイルを使用してもよいが、通常はメモリ上で扱う。

項目ごとに保持する情報:

- 実行状態（待機中、実行中、完了、失敗）
- 実行日時
- 結果本文
- HTTP ステータス
- エラー内容

実行日時とHTTPステータスは画面へ常時表示しないが、項目ごとの内部結果レコードとして保持する。HTTP通信を開始できなかった場合など、HTTPレスポンスを受け取れない失敗ではHTTPステータスを`0`とする。

完了した API 項目の結果アイコンをクリックすると、保持している直近の結果本文をクリップボードへコピーする。実行中は前回結果を内部に保持したまま、結果アイコンを非表示にする。

結果履歴の画面表示、複数結果の一覧表示、結果の個別削除は対象外とする。内部結果レコードはアプリ終了時に破棄し、永続保存は必要になった場合に追加する。

### 9.1 状態アイコンの種類

通常の定型文一覧に含まれる API 項目には次のアイコンを使用する。API 設定一覧画面の行操作とは区別する。

- 実行／再実行
- 実行中
- エラー
- 実行不可
- 実行結果保持

実行／再実行、実行中、エラーは同じ「状態アイコン領域」を使用し、一覧の一番右に固定する。実行結果保持アイコンは、状態アイコンのすぐ左に固定する。

```text
項目名                                      [実行結果保持] [状態]
```

- 状態アイコンの位置は状態によって移動させない。
- 実行結果保持アイコンが非表示でも、状態アイコンの位置は移動させない。
- 2つのアイコンの表示領域とクリック判定は分離する。
- アイコン同士の間隔は一定とする。
- `[Run]`、`[Copy]`などの文字列は項目名へ追加しない。
- 一覧は owner-draw など、項目本文と右寄せアイコンを独立して描画できる方式を使用する。
- 実行／再実行アイコンは緑、実行中アイコンは黄、エラーアイコンは赤で表示する。
- 実行不可アイコンはグレー、実行結果保持アイコンは青で表示する。
- 色だけに依存せず、実行は三角形、実行中は点列、エラーは×印、実行不可は禁止記号、結果保持は文書形状を維持する。選択行の背景色が変わっても各アイコンを判別できる色と線幅を使用する。

### 9.2 状態別の表示

| 状態 | 状態アイコン領域（一番右） | 実行結果保持（すぐ左） |
|---|---|---|
| 未実行 | 実行 | 非表示 |
| 実行中 | 実行中 | 非表示 |
| 成功 | 再実行 | 表示 |
| エラー、前回の成功結果あり | エラー | 前回結果を表示 |
| エラー、前回の成功結果なし | エラー | 非表示 |
| 必須資格情報なし | 実行不可 | 前回結果があれば表示 |

実行または再実行を開始したときは、実行結果保持アイコンを直ちに隠す。ただし、前回の成功結果は内部メモリから削除しない。

- 実行に成功した場合は、保持結果を新しい結果へ置き換えて結果保持アイコンを再表示する。
- 実行に失敗した場合は、前回の成功結果を変更せず、その結果があれば結果保持アイコンを再表示する。
- 前回の成功結果がなく、実行に失敗した場合は結果保持アイコンを表示しない。

### 9.3 クリック操作

通常の定型文一覧にある API 項目の行とアイコンの操作を次のように分ける。

- 行のシングルクリックは選択だけを行う。
- 行のダブルクリックは項目を実行する。
- 実行／再実行アイコンはシングルクリックで実行する。
- 実行結果保持アイコンはシングルクリックで保持結果をクリップボードへコピーする。
- 実行中アイコンをクリックしても反応しない。
- 実行中の行をダブルクリックしても反応しない。
- 実行不可アイコンまたは実行不可の行を操作した場合は通信せず、不足資格情報とAPI設定画面への導線を表示する。
- 結果保持アイコンが表示されていても、行のダブルクリックは結果コピーではなく再実行とする。

エラーアイコンをシングルクリックした場合、またはエラー状態の行をダブルクリックした場合は、エラー内容と「再実行しますか？」を確認メッセージに表示する。

- 「はい」を選択した場合だけ再実行する。
- 「いいえ」を選択した場合は状態と保持結果を変更しない。
- 再実行開始後は結果保持アイコンを一時的に隠す。
- 再実行も失敗した場合は、前回の成功結果を維持して再表示する。

### 9.4 クリップボードへの結果反映

API 実行開始時のクリップボード内容を保持し、実行完了時の内容と比較する。

- 実行完了時のクリップボードが開始時と同じ場合は、成功結果を自動コピーする。
- 実行完了時のクリップボードが空の場合も、成功結果を自動コピーする。
- 実行開始後にクリップボードが別の内容へ変更されていた場合は、自動コピーしない。
- 自動コピーしなかった場合も成功結果は内部に保持し、実行結果保持アイコンを表示する。
- ユーザーは実行結果保持アイコンをシングルクリックして、保持結果をクリップボードへコピーできる。
- エラー時は新しい結果をコピーしない。前回の成功結果がある場合は、その結果を結果保持アイコンから再コピーできる。

## 10. 通信エラーと再試行

- 通信中は待機状態を表示する。
- 通信中も定型文一覧の操作を妨げない。
- タイムアウトを用意する。初期値は 120 秒とする。
- タイムアウト時間は API 詳細の標準値として設定する。
- 認証エラーやリクエスト不正は自動再試行しない。
- 一時的な通信エラー、レート制限、サーバーエラーも初期実装では自動再試行しない。
- 将来的にエラー内容を判別し、再試行可能な場合だけ再試行する。

API ごとに処理時間の差があるため、将来的に Action 単位でタイムアウトを上書きできるようにする余地を残す。キャンセルは初期実装の対象外とする。

## 11. API 実行中の操作制限

初期実装では、API リクエストの重複実行と設定変更による不整合を防ぐため、API 実行中は API 関連の操作を一時的に無効化する。

### 無効化する操作

- API リストの選択
- API Action リストの選択
- API Action の実行
- API 詳細・Action 詳細の追加、編集、削除
- カテゴリの切替・カテゴリ設定（実行中項目と内部結果レコードの対応を維持するため）

### 解除するタイミング

次のいずれかになった時点で操作を再び有効化する。

- API 処理が完了した
- API 処理が失敗した
- タイムアウトした

API 実行中であることは画面上に表示する。キャンセル機能は初期実装の対象外とする。

認証方式の設定項目とAIによるAPI設定生成の基準は、[auth-spec.md](auth-spec.md) に定義する。

通常の定型文一覧は有効なままとし、通常項目の選択・コピーを継続できる。API項目の実行操作は実行中に受け付けない。カテゴリ切替だけは実行中項目と内部結果レコードの対応を保つため一時的に無効化する。

## 12. API キー・トークン

- API キーやトークンを Git、共通サンプル JSON、バックアップへ保存しない。
- 通常の設定ファイルやリクエストログへ保存しない。
- API 詳細画面から登録、変更できるようにする。
- 認証情報入力欄はマスク表示し、保存済みの秘密情報を画面へ復元しない。
- 認証情報入力欄が空の場合は保存済みの値を維持し、値が入力された場合だけ更新する。
- ネイティブ版では Windows の OS 管理機構を利用する。
- API設定の`authType`から必要な資格情報を判定する。APIキー・Bearerではtoken、Basic認証ではIDとPASSを必須とする。
- 必須資格情報が未登録の場合は、通信開始前から対象項目を実行不可として表示する。
- 実行不可アイコンまたは項目を操作した場合は、不足しているtoken、ID、PASSと、システムメニューの「API」から設定することを案内する。
- 資格情報の未登録は通信エラーと区別し、「再実行しますか？」の対象にしない。

保存先は Windows Credential Manager とする。設定 JSON、サンプル、バックアップには秘密情報を含めない。
