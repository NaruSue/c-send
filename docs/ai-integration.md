# c-send AI連携方針・拡張設計

> この文書は開発者・設計者向けの設計メモです。通常の利用者は、README、[はじめて使う人へ](first-use.md)、またはAPI利用者向けの各チュートリアルを参照してください。

## 1. この文書の位置付け

この文書は、c-sendの理念、AIとの責任分担、設定ファイルを中心とした拡張方針、将来のワークフロー・個人コンテキスト・企業向け拡張を定義する。APIの通信仕様は [API機能設計書](api/design.md)、設定JSONの構文は [API設定JSON仕様](api/config-spec.md) を正とする。

実装済みの機能と将来設計を混同しないよう、各項目を次のように区分する。

| 区分 | 意味 |
| --- | --- |
| 実装済み | v2.0のネイティブ版で利用できる機能 |
| 設計 | 次の実装単位として仕様を固める機能 |
| 将来 | 要件・安全性・対応OSを確認してから実装する構想 |

## 2. 理念

c-sendは、AIに何でも任せる自律エージェントではない。コピーした文章、定型文、プロンプト、API、個人のルールを利用者が組み合わせ、必要な変換を短い操作で実行して結果をクリップボードへ返す、ローカルファーストの個人用テキスト操作レイヤーである。

価値は、特定のAIサービスを囲い込むことではなく、利用者が自分の仕事・立場・相手・用語・定型処理に合わせて環境を作り、AIを交換可能な処理部品として使える点にある。メールの自動送信や無制限のエージェント実行を中心機能にしない。生成結果を確認して、メール、チャット、文書、Copilotなど利用者が選んだ場所へ貼り付ける。

## 3. AIとアプリの責任分担

| 担当 | 責任 |
| --- | --- |
| c-send | JSONの検証、認証情報のOS保存、通信、タイムアウト、実行状態、実行順序、クリップボード保護、エラー表示 |
| AI/APIサービス | 意味理解、翻訳、要約、言い換えなどの意味的変換、サービス固有の仕様 |
| 利用者 | APIの選択、キー取得、送信内容・プロンプト・個人ルールの確認、結果の利用 |
| 設定生成AI | 公式資料をもとにしたJSON・手順の作成支援。秘密情報を要求・保存・推測する権限は持たない |

AIの品質やAPIの料金・規約・データ利用はc-sendが保証するものではない。設定生成AIの出力も必ず利用者が確認し、c-sendのJSON検証と実行前の認証情報チェックを通す。

## 4. AIの得意・不得意を補う設計

AIは自然言語の意味変換を得意とする一方、複数条件の完全な同時適用、厳密な順序、同じ入力に対する再現性、機械的な置換・整列を保証しないことがある。これはAIの善悪ではなく役割の違いである。

したがって、次の原則を採用する。

1. 機械的に正確な処理はアプリ側で行う。
2. 意味を理解する処理はAI Actionに任せる。
3. AIへの依頼は「一つのAction、一つの目的」を基本とする。
4. 複数の目的は一つの巨大なプロンプトへ混ぜず、アプリが定義した順序で直列実行する。
5. 各段階の入力・出力・失敗を分離し、途中結果を追跡できるようにする。

例として「危険語を置換する」「女性向けの文体にする」「語尾に猫らしい表現を付ける」は、三つのAI Actionとして順番に実行する。プロンプト内の優先順位をAIに解釈させて一度に処理させない。

## 5. 公開リポジトリをAI向けの仕様パッケージにする

公開リポジトリはソースコード置き場だけでなく、AIが設定を生成・更新するための機械可読な仕様パッケージとして整備する。

利用者がAIへ渡す資料は、原則として次の組み合わせとする。

- c-sendの理念・利用方法・[API設定JSON仕様](api/config-spec.md)
- 対象APIの公式ドキュメント、エンドポイント、認証、リクエスト・レスポンス仕様
- 必要なら現在使用中の設定JSONとカテゴリサンプル
- 利用したい目的、モデル、入力・出力条件

AIへの依頼では、設定JSONだけでなく、キー取得、c-sendへの登録、カテゴリへの追加、Mock確認、実API確認、既知の制限まで出力させる。GitHubを参照させる場合は、アプリのバージョンと一致するリリースタグの資料を優先し、変更中のブランチを仕様の根拠にしない。

AIは未知の仕様を推測して補完してはならない。公式資料に不足がある場合は質問事項として返し、秘密情報の入力を求めない。出力は必ず「実装済み」「利用者が行う設定」「未対応の仕様」に分ける。

## 6. API設定JSONを正とする

APIサービス固有の処理をC++へ追加し続けない。アプリ本体は、HTTPメソッド、URL、JSON、レスポンス抽出、共通認証方式、タイムアウトなどの汎用機能だけを提供する。GeminiやOpenAIなどの違いは設定JSONで表現する。

設定画面は、JSONを人が確認・編集・検証し、認証情報を登録するための補助画面である。サービスごとに専用フォームや専用実装を増やさない。認証方式の選択、変更可能なキー名、必須資格情報の宣言も設定JSONで表現する。

未対応のOAuth、署名認証、SSE/WebSocket、multipart、ページングなどは、サービス固有のハードコードで回避せず、必要性を確認したうえで汎用機能として追加する。

## 7. 個人コンテキスト（自分DB）

### 7.1 目的

利用者固有の人物像、立場、相手、用語、禁止事項、文章規則をローカルの構造化データとして管理し、テンプレートや将来のワークフローから明示的に参照できるようにする。全データを無条件にAIへ送らず、項目またはActionが必要なコンテキストだけを選ぶ。

### 7.2 想定データ

- ペルソナ: 「主任。決定権は限定的だが進言できる立場」
- 相手・提出先: 「XX先生向け。丁寧語、1500文字以内、根拠を明示」
- 文体: 「語尾に『だっちゃ』を付ける」
- 用語集: 社内略語、製品名、翻訳語
- 禁止・置換語: 社内規則に基づく表現の置換
- プロジェクト・顧客ごとの定型ルール

データは設定JSONとは分離し、参照IDを通じて組み合わせる設計を基本とする。例: `style-daccha`、`recipient-professor-xx`、`glossary-product-a`。認証情報や個人情報は、公開サンプル・AIへの依頼文へ含めない。

## 8. 順序付きワークフロー（設計）

ワークフローはv2.0の実装範囲外であり、次期設計として扱う。入力を受け、決定的なローカル処理と一目的のAI Actionを順番に実行し、最後にテンプレート整形してクリップボードへ返す。

```json
{
  "mode": "workflow",
  "steps": [
    { "type": "input", "source": "clipboard" },
    { "type": "transform", "name": "normalize_width" },
    { "type": "transform", "name": "unique_lines" },
    { "type": "transform", "name": "sort_lines" },
    { "type": "api", "api": "openai", "action": "responses-create" },
    { "type": "template", "value": "```text\n{{value}}\n```" }
  ]
}
```

ローカル処理の候補は半角・全角変換、空行整理、重複行削除、行ソート、箇条書き、コードブロック化である。AI処理の候補は翻訳、要約、顧客向け表現、専門用語の説明などである。各ステップは成功・失敗・中間値を分け、失敗時は後続処理を勝手に続けない。任意のエージェントループや自動送信は採用しない。

## 9. クリップボードと外部アプリの境界

c-sendは生成結果をクリップボードへ返す。実行開始時と応答受信時でクリップボードが変わっていた場合は上書きせず、保持結果のアイコンから利用者が明示的にコピーする。外部メール・チャットへの送信は行わない。

自動送信を標準機能にしない理由は、認証や設定の負担、送信先の誤り、誤送信時の影響、メール以外にも結果を使える再利用性である。Outlook、Teams、CRM、Copilotなどへの貼り付けと送信は利用者が確認して行う。

将来の最小CLI連携として `/add "text"` を設計する。これは既定または事前設定したテキスト項目へ文字列を追加する単純な操作とし、複雑な管理APIにしない。現時点では未実装であり、実装済みCLIは [アプリAPI設計](app-api.md) の `/api` 操作だけである。

## 10. URL取得・スクレイピング（将来）

URLから本文を取得してAI入力へ展開する汎用`fetch`ステップを将来検討する。任意のcurl実行ではなく、c-sendのHTTP層で制御する。HTTPSを基本とし、localhost・プライベートネットワーク・file URL・過度なリダイレクト・巨大レスポンスを制限し、Cookieや認証情報を既定では送らない。HTMLの本文抽出、タイムアウト、利用規約・著作権、明示的なユーザー操作を考慮する。

## 11. 対応形態の役割

- ネイティブ版: v2.0のAPI実装、Windows Credential Manager、CLI、将来のワークフロー・監査を担う。
- HTA版: 追加導入が難しい環境向けの軽量な定型文・カテゴリ共有を担う。ネイティブ版のAPI機能を実装済みとは扱わない。
- PWA版: カテゴリ、テンプレート、サンプルの共有概念を利用する。ネイティブ版のAPI仕様を基準に、認証情報の保存とAPI通信をPWA版設計書へ定義する。
- スマートフォンキーボード: 将来のAndroid/iOS向け構想。入力内容を収集しないことを基本とし、API処理は明示操作に限定する。

設定JSON、テンプレート、カテゴリの概念は共有しやすく設計するが、認証・OS権限・通信の実装を無理に共通化しない。

## 12. 企業向け拡張（将来）

DLLは、OAuth/SSO、社内API、監査ログ出力などを追加するための拡張境界として検討する。DLLは同一プロセスで動くためサンドボックスではない。ABI・バージョン・機能宣言、許可リストや署名、エラー分離を必要条件とする。

監査ログはプラグイン任せにせずアプリ側の共通イベントとして扱う。日時、利用者・端末識別子、カテゴリ・項目・ワークフロー、API・Action、成否、HTTPステータス、所要時間、エラーを記録し、token・パスワード・送信本文は既定で保存しない。必要な場合もハッシュや管理者設定で制御する。

企業向けの書き込み連携は、プレビュー、利用者承認、許可された送信先、監査記録を経る。無確認のメール送信や外部システム更新を標準機能にしない。

## 13. 拡張・貢献のルール

新しいAPIやカテゴリを追加する場合は、設定JSON、公式資料へのリンク、認証手順、サンプル、Mockケース、制限事項、変更日を同梱する。アプリ本体のサービス固有分岐は追加しない。API仕様変更時は、対象サービスの公式資料、現在のJSON、同じリリースタグのc-send仕様を再確認する。

実装前の提案はこの文書の区分を更新し、実装後に「実装済み」へ移す。公開サンプルには実キーを含めず、AI生成用の説明と利用者が確認すべき点を明記する。

## 14. ロードマップ

1. 実装済み: ネイティブ版の汎用API、認証情報のOS保存、JSON設定、テンプレート、状態表示、`/api` CLI、Mock CI。
2. 設計: JSON-firstの設定編集、個人コンテキスト、自動的に順序を守るワークフロー、最小CLI `/add`。
3. 将来: 汎用URL取得、OAuth/署名などの認証拡張、DLL、監査、企業向け承認付き書き込み、スマートフォンキーボード。

この順序を守り、AIサービスを増やすこと自体を目的にせず、利用者が自分の環境を安全に組み立てられることを優先する。
