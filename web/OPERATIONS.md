## Application shape

Keep the first version as one PHP application. Same-origin PHP pages handle input and moderation; `template.php` serves JSON. There is no SPA, separate API host, or frontend build step. The template manager opens to a selectable list. Selecting a row opens that template's editor; `新規追加` opens a blank editor. Its navigation is a desktop sidebar and a floating menu on mobile. Users enter a template title, item name, comma-separated tags, mode, and content. PHP creates the c-send-compatible document and stores the complete document in `template_revisions.document jsonb`.

## Shared screen and navigation rules

Apply these rules to every signed-in management screen so the template manager and admin pages behave and look like one site. The admin menu uses separate pages: `/admin-users.php`, `/admin-templates.php`, and `/admin-reports.php`. Growing lists use pagination (50 users, 25 templates, or 25 open reports per page).

1. **Use one navigation, without duplicate link bars.** Keep the brand in the global header. Put destinations in one shared accordion menu; do not repeat those links in a second horizontal header bar.
2. **Keep the same menu placement across pages.** Desktop uses a left sidebar. Mobile (viewport 700px and narrower) hides the sidebar and uses a floating menu button whose panel contains the same accordion groups and links. The floating panel closes after choosing a destination, tapping outside, or pressing Escape.
3. **Group destinations consistently.** Use `サイト` (home and public templates), `テンプレート管理` (list and new template when signed in), `管理` (separate user, template, and report pages for admins), and `アカウント` (login or logout). Automatically expand the group containing the current page; allow other groups to collapse or expand.
4. **Make each menu item a separate destination.** The admin menu opens separate pages for users, templates, and reports; do not place these growing lists together on one page. Use the same order, wording, and destination on desktop and mobile.
5. **Keep the primary workflow predictable.** List pages show records and their key status. Selecting a record opens its detail/edit/action view; creation starts from an explicit `新規追加` action. A back-to-list link returns to the originating list. Do not combine navigation, record list, and long edit forms into one undifferentiated block.
6. **Keep forms aligned across screen sizes.** Each field label sits above its control, controls fill the available content width, and text areas remain within the content column. Related actions belong with their form. Avoid fixed-width fields that overflow on mobile.
7. **Preserve accessible interaction.** Use native accordion controls and ordinary links; the mobile menu button exposes `aria-expanded` and `aria-controls`, supports keyboard use, and closes on Escape/outside tap. Do not rely on hover alone.

When adding a management screen, update its navigation using these shared rules rather than inventing a page-specific menu. If the rule changes, update this section first and then align every management screen to it.

Each site record represents one c-send item and is edited/reviewed independently, even though c-send internally represents data in `items` arrays. A template detail/editor is not a set editor. Combining several independent records concatenates their `items` arrays in selection order only when the visitor creates a selection URL.

## URL behavior

- One template: `GET /c-send/t/{uuid}.json`
- Selected templates: `GET /c-send/t/selection.json?ids={uuid},{uuid}`
- The public selection builder accepts an optional `リストのタイトル` (up to 120 Unicode characters). It adds the value as the root `groupname` in the generated JSON URL response; omitting it keeps the existing `ids`-only behavior. The fixed sample feed uses `groupname: "公式サンプル"`.
- Content page: `/c-send/t/view.php?id={uuid}`. Public visitors see item content, tags, mode, update time, revision, and the author's profile link. JSON/edit/report actions are shown only to signed-in users where allowed.
- The selection page writes the ordered IDs into a URL in the browser. The server stores neither that set nor per-user selection history.
- Every GET checks current publication and owner status, reads the current revision, and generates a fresh `createdAt`. JSON responses include a weak `ETag` based on `format`, `version`, `groupname`, and `items` (excluding the per-request `createdAt`); matching `If-None-Match` requests receive `304 Not Modified`. The PHP origin still sends `Cache-Control: no-store`; the Cloudflare Cache Rule overrides it at the edge.
- Cloudflare Cache Rule `loose.bz JSON cache` is active: hostname equals `loose.bz` and URI path wildcard `*.json`, cache eligibility enabled, Edge TTL overrides origin cache-control at 5 minutes, and Browser TTL overrides origin at 5 minutes. Responses now expose `Cache-Control: max-age=300`. The default cache key includes the query string, so different selection `ids` URLs have separate entries. On 2026-10-08, the selection URL returned `MISS` then `HIT`; changing ID order produced a separate `MISS` then `HIT`. After the five-minute TTL expired, Cloudflare returned `REVALIDATED` using the origin ETag, followed by `HIT`. Updated JSON can remain cached for up to five minutes. The rule matches `.json` paths anywhere on the apex `loose.bz` host.
- The Nginx JSON location sends `Access-Control-Allow-Origin: *` and `Access-Control-Expose-Headers: ETag`. On 2026-10-08, both `HEAD` and `GET` returned the exposed ETag on cache-miss URLs after the Nginx update. Previously cached edge responses may omit the new expose header until refreshed.
- Edits retain the same stable UUID and create a revision for review. A pending template is omitted from public output; after approval, its existing URL serves the approved revision.
- Upload accepts a one-item c-send2 Export JSON file up to 1 MB from the blank or selected template editor. A blank editor creates a new template using the entered site title; a selected editor supplies the existing template identity. No site-specific ID is added to c-send2 JSON. Comparison ignores root metadata and item usage/source fields (`usageCount`, `lastUsedAt`, `sourceName`). An identical upload leaves revision and `updated_at` unchanged; changed content creates a revision, updates `updated_at`, and moves the template to `pending` for review. The site's display title remains unchanged.
- UUIDs are catalog metadata only. Do not add them to c-send JSON unless a client compatibility need is demonstrated.
- URLs and published template JSON are public. JSON responses use `Access-Control-Allow-Origin: *` so browser-based c-send clients can read them; the JSON nginx location must also send `Access-Control-Expose-Headers: ETag` so cross-origin JavaScript can read the validator. The location should retain both headers on error responses with `always`. No credentials are allowed or needed. CORS is a browser read policy, not authentication or access control; all published templates are already publicly retrievable.
- Live CORS check on 2026-10-08: before the Nginx update, `loose.bz` JSON responses lacked `Access-Control-Expose-Headers`. After deploying the updated JSON location and reloading Nginx, cache-miss `GET` and `HEAD` responses include `Access-Control-Expose-Headers: ETag`. Previously cached edge responses may omit this header until refreshed. `HEAD` is a CORS-safelisted method and needs no preflight when sent without custom request headers ([MDN CORS guide](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS)).

## Accounts and moderation

Authentication uses PHP `password_hash` hashes, CSRF tokens, secure HTTP-only same-site cookies, and session ID rotation. Users can sign in with Google or a verified email/password account. Email registration and password reset require a short-lived six-digit code sent by email. Initial IDs are `admin` and `user`; their generated passwords were provided separately to the operator after first deployment. Save them in an approved password manager. Never put passwords in this document or repository. The admin page follows the shared screen and navigation rules above, linking to users, templates, and reports.

Google sign-in also provides self-registration. Configure `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, and the optional `GOOGLE_LOGIN_USERS` bootstrap mapping in `/etc/csend-template/google-oauth.php` (outside the document root). The verified Google account `narusue2008@gmail.com` maps to the existing `admin`; all other first-time Google accounts create regular users with opaque usernames. A Google subject is the stable identity key. Do not claim an existing account based on email alone. The OAuth web client must allow `https://loose.bz/c-send/t/google-callback.php` as an authorized redirect URI. The flow requests only `openid email`, verifies the email with Google's userinfo endpoint, and starts the normal site session. The callback's `.php` URI is handled directly by Nginx; `/c-send/t/google-login` is the user-facing start URL. Never copy the client secret into this repository or a public file. The deployment installer creates this separate config only when absent so later deployments preserve its credentials and account mappings.

Email registrations use a separate verification flow. Migration `011_email_accounts.sql` adds optional verified email and public profile fields plus short-lived, one-use email code challenges. PHP sends mail through the host's local sendmail/Postfix service; set `MAIL_FROM` in `/etc/csend-template/config.php` if the default `noreply@loose.bz` sender should change. The code flow stores only password-hashed verification codes, expires them after 10 minutes, limits sends to five per address per day and one per minute, and allows at most eight code attempts. Google-only accounts continue to use Google login and do not receive email password-reset codes. `deploy-template-ui.ps1` applies the migration and installs the auth/profile/admin UI together.

Email addresses are encrypted at rest with AES-256-GCM. The first deployment creates a random 32-byte `EMAIL_ENCRYPTION_KEY` in `/etc/csend-template/.env`, outside the document root, with permissions `root:www-data 0640`; later deployments preserve that key. Keep a secure, independent backup of this key; losing it makes encrypted email addresses unrecoverable. A keyed HMAC lookup value supports login, uniqueness checks, and email rate limits without storing a searchable plaintext address. Migrations `013_email_encryption_columns.sql` and `014_email_encryption_indexes.sql`, together with `bin/encrypt-email-data.php`, convert existing user, Google-link, verification-challenge, and email-send-history addresses. Deployment verifies that addresses decrypt and that the email login lookup and password check work using a temporary transaction that is rolled back. Never place the production key in the repository, deployment archive, or database backup.

The PWA API is deployed separately with `deploy-pwa-api.ps1`; it installs `/c-send/api/v1/`, migration `007_pwa_api_auth.sql`, the `.tmp` login bridge, and Nginx routes without changing PWA static assets or database credentials. Registration and Google authentication remain on `.tmp`; no additional Google redirect URI or OAuth client is needed. PWA saves stay in IndexedDB by default. When signed in, users may opt in per item in the create/edit screen to upload a private draft using the authenticated API; the option is hidden while signed out. Existing device items are never uploaded just by signing in. Publication remains a separate action in `.tmp`. See `api/README.md` for Authorization Code + PKCE and private-draft template API details.

Keep user registration on `.tmp` for this release. A future `.api` registration endpoint may let PWA and native clients register directly, but it must share the existing users and Google identity records.

User templates begin as drafts and are submitted for administrator review. Admins can publish/reject templates, suspend/restore templates, suspend/reactivate accounts, and process reports. Templates are shown as a compact list with Japanese status labels; each row expands to show content, status transitions, actor, time, and any optional reason. Actions are limited to those valid for the current state. Login requests are rate-limited by nginx at 10 per minute with a burst of 5 per source address. Reporting currently requires login. Moderation events record actor, subject, action, reason, prior state, new state, and time.

Public user guidance is rendered by `public/guide.php`, `public/terms.php`, and `public/privacy.php` through the common site layout. Signed-in users receive the standard navigation and signed-out visitors retain the shared header without a menu. Legacy `/c-send/*.html` URLs redirect to these pages. Keep the guide and terms aligned with the actual publication review: submissions are reviewed before publication, focusing on spam, materially duplicate submissions, operational abuse, and technical validity. Content themes alone are not a blanket disqualification. Published items are public by URL, and the service cannot prevent copying them to external services. The privacy page must explain that PWA templates stay local unless the signed-in user explicitly chooses per-template account sync or requests an account backup.

## Data and retention

The database retains account identifiers and password hashes, template JSON and revisions, publication state, reports, and moderation events. It does not store selection URLs or selected ID combinations. The c-send origin access log now includes query strings for campaign attribution; Cloudflare or other upstream proxy/CDN logs are separate and must be checked independently.

Automated PostgreSQL backups, restore verification, account deletion rules, revision retention, and report retention are not configured yet. Decide these before treating the service as production-ready. This deployment is a small prototype.

## Deployment notes and recurrence prevention

- `prepare-deploy.ps1` packages files and generated passwords in a local temporary directory; it does not run the app locally. It uses Windows `tar.exe` to create a Linux-compatible tar.gz. Do not substitute `Compress-Archive`: it creates ZIP entries with Windows path separators that Linux tools did not extract as expected. Include static PWA assets with `-IncludePwa`; updating only `/c-send/pwa/` does not require the PHP/database installer.
- For OAuth-only updates to an already-installed instance, use `deploy-google-auth.ps1 -SshTarget <configured-SSH-target> -GoogleClientId <client-id>`. It transfers only login/router/OAuth PHP files and the Nginx location include; it does not touch PostgreSQL, DB credentials, portal, or PWA. It prompts for the client secret without echoing it (or reads it from the clipboard with `-SecretFromClipboard`), writes it only to `/etc/csend-template/google-oauth.php` on the server, and maps `narusue2008@gmail.com` to the confirmed existing `admin` account.
- Run `php -l` on every public PHP file before nginx reload. The initial deployment caught an unmatched closing parenthesis in `dashboard.php`; validate all entry points before opening the route.
- Do not wrap the template selector in a form while rendering report forms inside each template row. Nested HTML forms are invalid and caused iOS Safari to detach the URL-generation button from its submit handler. The selector now uses a standalone click button and exposes the generated URL as both text and a link.
- Keep the copy-to-clipboard control beside the generated URL field. Use the Clipboard API on secure contexts and retain a select-and-copy fallback for mobile Safari; announce the result with an accessible status message.
- Keep admin templates as a compact list: show title/state/owner/date at a glance, and put preview, history, and actions inside a per-row disclosure.
- Keep DB configuration outside the web root. Keep private helpers readable by `www-data` but outside the document root.
- The schema was first created by PostgreSQL's administrative role. Grant the app role table/sequence privileges and default privileges. The installer now does this idempotently.
- Do not recreate initial accounts on redeploy. The installer checks for `admin` and `user`; existing password hashes stay unchanged.
- Back up `/etc/nginx/conf.d/loose.bz.conf` before editing. Run `nginx -t` before `systemctl reload nginx`.
- Verify `/c-send/t/`, `/login.php`, `/browse.php`, and a selection URL over HTTPS. A not-yet-published selection should return a JSON 404, not an HTML/PHP error.
